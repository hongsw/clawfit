# Research Watch: multica — Open-Source Managed Agents Platform with Team-Coordination Semantics over Multi-Vendor Coding Agents

- Repo: https://github.com/multica-ai/multica
- Also see: https://github.com/multica-ai/multica/blob/main/SELF_HOSTING.md (self-hosting deployment guide); https://github.com/multica-ai/multica/blob/main/CLAUDE.md (authoritative architecture spec for the codebase); `docs/research-watch/2026-04-13-anthropic-managed-agents-hosted-stable-interfaces.md` (Anthropic's "managed agents" framing — first appearance of the term in this taxonomy); `docs/research-watch/2026-05-09-helmor-multi-agent-dev-workbench.md` (adjacent GUI desktop harness wrapping multiple coding-agent CLIs); `docs/research-watch/2026-05-09-opencode-open-source-coding-agent.md` (peer signal on provider-agnostic execution); `docs/reference-levels.md` line 304 + line 377 (prior L2 placement of multica at the ~6k-star and ~22k-star tracking points)

## Why this is worth watching

multica is structurally distinct from every other multi-vendor coding-agent wrapper currently in the taxonomy because it does not present itself as a harness or a UI shell — it presents itself as a **task-management platform with agents as first-class polymorphic assignees alongside humans**. The CLAUDE.md spec is explicit: "Multica is an AI-native task management platform — like Linear, but with AI agents as first-class citizens" with "Assignees are polymorphic — can be a member or an agent. `assignee_type` + `assignee_id` on issues." This is a different architectural primitive than what Helmor, oh-my-*, DureClaw, or even opencode model: the **kanban board state machine, issue lifecycle, squads/leader routing, and workspace multi-tenancy** are the product surface — the agent CLIs are subordinate execution substrate auto-detected on PATH. At 31,905 stars (+410 today, GitHub Trending Daily #11 on 2026-05-24) and a daily release cadence (v0.2.30 → v0.3.6 across May 11–22, 2026; 14 releases in 12 days), this has already crossed the 5k-star registry threshold by ~6.4x and is the second clear L3 candidate after obra/superpowers that is built as a team-coordination application rather than a methodology + skills bundle.

## What stands out immediately

- **31,905 stars, 3,900 forks, modified Apache-2.0 license.** Verified 2026-05-24. The license is not standard Apache-2.0: the LICENSE file's first paragraph reads "Multica is licensed under a modified version of the Apache License 2.0, with the following additional conditions" — explicitly prohibiting offering multica as a hosted SaaS service to third parties without authorization, requiring frontend logo/copyright preservation, and reserving the producer's right to modify license terms. This places multica in the **modified-Apache / commercial-restricted** license sub-cluster (similar in posture to Elastic License or BSL-derivatives), not the open-license sub-cluster that the prior reference-levels.md L2 entry implicitly assumed. Internal organizational use is unrestricted; competing hosted offerings are not. This is a material distinction for `governance_need: hard` profiles that screen on license terms.

- **Stack: Go 42.9% (backend) + TypeScript 50.9% (frontend) + PostgreSQL 17 with pgvector + Next.js 16 + Electron desktop + Expo/React Native mobile.** From CLAUDE.md: "Go backend + monorepo frontend (pnpm workspaces + Turborepo) with shared packages." Backend uses Chi router, sqlc, gorilla/websocket. The pgvector dependency signals embedded vector-search capability for the skills/memory layer, though the README does not document the indexing strategy. The monorepo includes `server/`, `apps/web/`, `apps/desktop/` (Electron), `apps/mobile/` (Expo, independent), `packages/core/` (headless business logic, zero react-dom), `packages/ui/`, and `packages/views/` — a deliberate three-surface (web + desktop + mobile) deployment topology, not a single-surface tool.

- **Auto-detection of 11 agent CLIs on PATH.** The daemon "auto-detects agent CLIs (`claude`, `codex`, `copilot`, `openclaw`, `opencode`, `hermes`, `gemini`, `pi`, `cursor-agent`, `kimi`, `kiro-cli`) on your PATH." Verified from README. This is the widest cross-vendor coding-agent coverage seen in a single coordinating system in this taxonomy — broader than Helmor (3 providers: Claude Code, Codex, Cursor) and broader than opencode (which is itself a base runtime that abstracts over LLM providers, not over agent CLIs). The auto-detection model means multica does not bundle or version-pin agent binaries — the opposite trust-model choice from Helmor's SHA256-pinned bundles.

- **Squads as a first-class coordination primitive.** The squad feature (v0.3.0 MVP, May 14) groups agents and humans under a leader agent; work is assigned to the squad rather than to individuals, enabling stable routing as squad composition changes. This is structurally similar to the `assignee_type` polymorphism but at the team level — a routing abstraction that decouples task assignment from individual identity. No other tool currently tracked exposes squad-as-routing-target as a first-class concept (Octopal models group chat; agency-agents models 12 professional divisions as a static org chart; neither implements squad-leader routing semantics).

- **Skill compounding model.** Per README: "Every time an agent solves a problem, that solution can be saved as a reusable skill — a playbook that any agent on the team can reference later." The exact skill format (whether SKILL.md-compatible with the Agent Skills open standard, or a multica-proprietary format) is not documented in the README or AGENTS.md fragments accessible without cloning. **Claim to inspect:** if multica skills are SKILL.md-format-compatible, this would make multica the first L3 team-coordination platform to natively consume the Agent Skills open standard at the team-shared-capability layer — a structural pattern not yet observed in the taxonomy. The pgvector dependency suggests skills may be indexed for retrieval rather than enumerated, which would be a meaningful sub-type difference from agency-agents' enumerated persona pack.

- **Full task lifecycle with WebSocket progress streaming.** States: enqueue → claim → start → complete | fail. Real-time progress streamed over WebSocket via gorilla/websocket. The daemon runs locally and reports back to the server; the server fans out to web/desktop/mobile clients. This is a non-trivial distributed-system shape: the orchestration plane (server, kanban state) is separated from the execution plane (local daemon, agent CLI invocation). For self-hosted deployments, both planes can run on the user's infrastructure; for Multica Cloud, the orchestration plane is hosted and the execution plane remains local to each developer's machine.

- **Hybrid deployment: self-hosted Docker Compose + Multica Cloud.** From SELF_HOSTING.md: self-hosted requires Docker, Docker Compose, PostgreSQL 17 with pgvector, Go runtime, Node.js, and at least one agent CLI. "Each user who runs AI agents locally also installs the `multica` CLI and runs the agent daemon on their own machine" — even in the self-hosted topology, the agent execution stays local to the developer's workstation. Migration path between self-hosted and cloud is explicit: `multica setup` reconfigures the CLI. This is the **first L3 candidate in this taxonomy with a co-designed self-hosted + cloud deployment story** at the team-coordination layer (obra/superpowers is methodology-only; gitagent is a spec, not a deployed platform; AGENTS.md is a format, not a service).

- **Daily release cadence at v0.3.x.** 14 releases across May 11–22, 2026 (v0.2.30 through v0.3.6). v0.3.0 shipped the Squad feature MVP; v0.3.5 added a two-layer timezone architecture for distributed scheduling; v0.3.6 introduced "v3 onboarding — thin server, frontend-orchestrated welcome" and a cloud runtime fleet proxy API. The cadence is comparable to Helmor (45 releases in <1 week at the v0.14–v0.20 range) — both signal active iteration, not stable maintenance. At v0.3.x the API surface is pre-1.0 and breaking changes are likely; the CLAUDE.md `parseWithFallback` + "enum drift downgrades, not crashes" pattern for desktop-vs-backend compatibility is itself evidence that the team is engineering around frequent backend churn.

- **No MCP integration documented.** Neither the README, AGENTS.md, nor CLAUDE.md (as fetched) reference MCP as either a server-side capability surface or a client-side tool-use mechanism. multica auto-detects agent CLIs but does not appear to register itself as an MCP server that those agents can call back into. **Claim to inspect:** absence of MCP is anomalous for a 2026-05-vintage coordination platform — either (a) MCP is present but undocumented in surface-level files, (b) the team has chosen to coordinate via the CLI invocation surface rather than via MCP, or (c) MCP integration is planned but unshipped. The absence is worth verifying directly before classification depends on it.

- **Polymorphic assignee model is the load-bearing schema choice.** `assignee_type` + `assignee_id` on the issues table means a single column-pair handles both human and agent assignment. This is a different schema choice than maintaining separate `human_assignee_id` and `agent_assignee_id` columns — it commits the data model to treating humans and agents as interchangeable at the assignment layer. Consequences include: (1) every UI that displays an assignee must handle both types; (2) every notification/comment path must work for both; (3) audit logs cannot distinguish human vs. agent actions without explicit `assignee_type` checks. This is the schema-level expression of the "agents as first-class citizens" framing.

- **Two-installation footprint per user.** Self-hosted teams need (1) the central multica server (one instance per team/org) and (2) the multica CLI + daemon on each developer's machine. This is heavier than a single-instance harness (Helmor, oh-my-*) and lighter than a full enterprise platform (Gemini Enterprise Agent Platform). The two-installation model is necessary because agent execution stays local to each developer's workstation — the server cannot run the agent CLIs on behalf of users without losing the developer's local context (git working tree, credentials, environment).

## Why clawfit should care

**1. multica resolves the "team coordination over multi-vendor coding agents" gap that is currently underexpressed in the L2/L3 taxonomy.** The existing L2 row places multica alongside oh-my-*, DureClaw, SuperClaude, and Archon — but those are predominantly **single-user or single-workstation harnesses**. multica is structurally an L3 team-coordination application (workspaces, polymorphic assignees, squads, kanban state machine, multi-tenancy via `X-Workspace-ID`) that happens to also include an L2 execution-plane daemon (the local CLI orchestrator). The prior reference-levels.md entry at line 304 — written when multica was at ~6k stars and the L2 reading was defensible because the team-coordination layer was thinner — should be re-examined. Today's primary read is **L3 primary with L2 secondary**, inverting the prior classification. This is a candidate map mutation, flagged but not applied per the single-signal-promotion-prohibited rule and the L3-vs-L2 boundary requiring a deliberate calibration cycle.

**2. The polymorphic-assignee primitive is a clawfit recommendation-engine signal, not just a feature.** Current clawfit scoring axes do not express "this platform treats agents as routable work-receivers alongside humans." For team profiles where the intended deployment is **human-agent mixed teams with shared kanban**, multica is the first tool in the registry that natively models this — most other tools either (a) treat agents as autonomous executors with no shared workboard, or (b) treat agents as IDE assistants subordinate to a human user. A candidate new axis `coordination_model ∈ {single_user, multi_user_no_shared_state, polymorphic_assignment, leader_routed_squad}` would make this expressible.

**3. The auto-detect-on-PATH model is the opposite trust-model choice from Helmor's SHA256-pinned bundles — both are valid, and the choice is recommendation-relevant.** For `governance_need: hard` profiles with strict supply-chain controls, Helmor's pinned-bundle model is preferable. For teams that already maintain their own CLI installs and want a coordinator that doesn't fight them, multica's auto-detection is preferable. clawfit's current registry has no `cli_distribution_model ∈ {bundled_pinned, auto_detect_path, install_on_demand}` axis to express this, and the trade-off is real: pinned bundles give reproducibility but force upgrade lag; auto-detection gives flexibility but trusts the user's PATH.

**4. The modified-Apache license places multica in a different governance bucket than the rest of the L3 cohort.** obra/superpowers, agency-agents, AGENTS.md, gitagent are all standard open licenses (MIT or Apache-2.0). multica's commercial-restricted Apache variant is closer to the BSL/Elastic License posture and explicitly prevents third-party hosted resale. For most teams this is irrelevant (internal organizational use is unrestricted), but for `governance_need: hard` profiles with compliance review pipelines, "modified Apache-2.0 with commercial restrictions" requires legal review where standard Apache-2.0 typically does not. The license sub-type granularity is not currently captured in the registry.

**5. 11-CLI coverage means multica is a vendor-neutrality signal at the team-coordination layer.** Just as the Agent Skills open standard signals vendor-neutrality at the capability layer (L4b, 35+ runtimes) and OpenSpec signals vendor-neutrality at the governance layer (L3, 30 tools), multica's 11-CLI auto-detection signals vendor-neutrality at the **team-coordination layer**. The 2026-05 pattern of "portable, vendor-neutral artifacts/platforms consolidating at every layer simultaneously" (noted in reference-levels.md re: Agent Skills + OpenSpec) now has a third instance: vendor-neutral coordination over vendor-specific execution. This is a candidate addition to the 2026-05 patterns meta-note, deferred pending a second team-coordination platform with comparable cross-vendor coverage.

**6. The "managed agents" naming convention now spans first-party hosted (Anthropic Managed Agents, 2026-04-13) and open-source self-hosted (multica, 2026-05-24).** The term has crossed the boundary from vendor-marketing into category-name. clawfit's current statefulness axis (`session` vs `stateless`) was flagged in the Anthropic Managed Agents entry as potentially needing a `managed_hosted` third value; multica suggests a fourth: `managed_self_hosted`. The distinction matters because the network/data-residency posture differs sharply: managed_hosted requires data egress to the vendor; managed_self_hosted keeps everything on-prem.

## Preliminary interpretation

Current best reading:

- **Level 3 — Team harness / executable SSOT / governance layer (primary).** multica's primary architectural surface is team coordination: workspaces with multi-tenancy, polymorphic assignees, squad-leader routing, kanban issue lifecycle, shared skill library. These are the defining properties of L3 — "where LLM usage stops being just a personal tool habit and becomes a team operating system" (reference-levels.md L3 definition). multica is closer in shape to a deployed Linear-style application than to a harness or wrapper. The CLAUDE.md framing "AI-native task management platform — like Linear, but with AI agents as first-class citizens" is the team's own statement of intent, and it matches the architectural evidence.

- **Level 2 — Meta wrappers / harnesses / orchestration layers (strong secondary).** The local daemon that auto-detects 11 agent CLIs, supervises their invocation, manages the task lifecycle (enqueue → claim → start → complete/fail), and streams progress over WebSocket is unambiguously an L2 harness component. multica embeds an L2 harness as its execution substrate. This is why the prior reference-levels.md placement at L2 was defensible at the ~6k-star tracking point — the L2 component is real and load-bearing. The classification shift to L3 primary at the 31.9k-star point reflects that the team-coordination surface has matured faster than the harness surface (squads, polymorphic assignees, multi-tenancy, multi-workspace are all L3 features added after the initial harness MVP).

- **Not L1.** multica does not implement agent reasoning, LLM invocation, or tool execution directly. All agent behavior is delegated to the auto-detected CLI binaries.

- **Not L4.** While skills are compounded into a team-shared library, this is a consumer of capability artifacts, not a producer of capability primitives. The pgvector-backed indexing (if used for skills) would be an L4a/L4b implementation detail rather than a primary L4 contribution. Whether multica skills are SKILL.md-compatible is a claim to inspect before any L4b cross-listing.

- **Not L5.** PostgreSQL with pgvector enables vector retrieval, but this is plumbing for the skills/kanban layer rather than a memory/context substrate that agents consume. multica is not an agent-memory product; it is a team-coordination product that happens to store team-shared skills.

- **Not L6/L7.** Standard Next.js + Electron + Expo presentation; no novel interface modality.

- **Sub-type candidate: open-source managed agents platform.** Distinguished from L3 methodology-and-skills bundles (obra/superpowers, agency-agents) by being a deployed multi-user application with kanban semantics; distinguished from L2 single-user harnesses (Helmor, oh-my-*) by polymorphic assignment and squad routing; distinguished from first-party hosted offerings (Anthropic Managed Agents, Gemini Enterprise Agent Platform) by open-source + self-hostable deployment. Anchor sample for this sub-type. Sub-type formalisation requires a second independent open-source team-coordination platform with comparable kanban-state-machine and polymorphic-assignment semantics.

- **License sub-cluster: modified-Apache / commercial-restricted.** First entry in this taxonomy with the modified-Apache posture at the L3 layer. Most L3 entries are MIT/Apache-2.0; placing multica in a license sub-cluster previously occupied only by some L1 enterprise tools (Sierra AI, some hyperscaler stacks) is itself a signal that the L3 layer is commercializing.
