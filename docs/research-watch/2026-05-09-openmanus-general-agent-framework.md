# Research Watch: OpenManus — General-Purpose Open-Source Agent Framework

- Repo: https://github.com/FoundationAgents/OpenManus
- Also see: https://foundationagents.org/projects/openmanus/ (org page); https://deepwiki.com/FoundationAgents/OpenManus (architecture deep-dive); https://llmmultiagents.com/en/blogs/OpenManus_Technical_Analysis (technical analysis); `docs/research-watch/2026-05-03-microsoft-agent-framework-1.md` (related: multi-agent harness at comparable scope); `docs/research-watch/2026-05-01-tradingagents-financial-multiagent-framework.md` (related: domain-specialized multi-agent at similar star tier)

## Why this is worth watching

OpenManus reached 56.2k stars (9.8k forks, MIT, Python 97.8%) built by the core MetaGPT contributor team — including Xinbin Liang and Jinyu Xiang — reportedly shipping a working prototype within 3 hours of the "Manus" invite-only launch as an open counter-offer. At 3 releases (v0.3.0 latest, April 2025), the release cadence is thin relative to its star mass, suggesting a viral capture event rather than sustained engineering output comparable to, say, opencode (791 releases). The framework is noteworthy not for production depth but for representing the MetaGPT team's architectural thesis about general-purpose agent construction — an inheritance-based agent specialization model layered over a ReAct think-act-observe loop — as a portable, provider-agnostic, multi-capability runtime.

## What stands out immediately

- **56.2k stars, 3 releases, Python-dominant (97.8%).** High star mass relative to a very shallow release history. This ratio (approximately 18.7k stars per release) is among the highest in the tracked taxonomy — a signal of viral adoption on a minimal codebase, not iterative production hardening. Compare: Ruflo at 38.8k stars / 1,471 releases; opencode at 157k stars / 791 releases.
- **Agent class hierarchy via inheritance.** `BaseAgent → ReActAgent → ToolCallAgent → {Manus, MCPAgent, BrowserAgent, DataAnalysis, SandboxManus}`. The design is compositional but inheritance-first rather than plugin-first. This contrasts with harness-style frameworks (Ruflo, deepagents) that wire agents externally. All agents share the same think-act cycle and tool-calling interface via `ToolCollection` as a runtime registry.
- **Three operational modes, not one.** `main.py` (general agent), `run_mcp.py` (MCP tool integration), `run_flow.py` (experimental multi-agent). The split is architectural: multi-agent is explicitly flagged as unstable. This is a claim-to-inspect: the multi-agent pathway has not been independently evaluated for production reliability.
- **MCP as client, not server (primarily).** `MCPAgent` dynamically connects to external MCP servers to load tool definitions at runtime. An MCP server implementation exists (`app/tool/mcp/mcp_server_implementation`) but is not the primary interface. OpenManus is an MCP consumer, not an MCP host — relevant for clawfit profiles that distinguish tool-use surfaces from tool-providing surfaces.
- **Daytona sandbox for isolated execution.** `SandboxManus` uses Daytona for untrusted code and browser automation. This is the security isolation mechanism. Claim to inspect: whether Daytona is a hard dependency or an optional plugin, and how isolated execution is governed for non-Daytona deployments.
- **Playwright-backed browser automation + vision model routing.** Browser interaction (`BrowserAgent`, `BrowserUseTool`) uses Playwright. Vision tasks are routed to a separately configured vision model endpoint (GPT-4o mentioned in sample config). The two-model config (text LLM + vision LLM) is unusual and not addressed in most registry frameworks. Requires config.toml with explicit endpoint separation — not zero-config.
- **Dependencies: anthropic-computer-use, browser-use, crawl4ai.** The capability surface is assembled from upstream projects rather than original implementation. This is a design choice aligned with the "open ground" framing, but it means OpenManus's browser and vision capabilities are bounded by what upstream projects expose, not by original engineering.
- **No benchmarks in primary docs.** No SWE-bench, GAIA, or task-completion metrics published in the README or releases. This is a notable gap relative to peers: OpenHands (which the same ecosystem acknowledges) cites ~66% SWE-Bench Verified with Claude Sonnet. OpenManus makes no comparable claim.
- **OpenManus-RL companion project.** A separate RL-based fine-tuning project developed with UIUC researchers. Suggests the team's longer-term direction is toward self-improving agents, not just multi-capability orchestration. This is a research-horizon signal, not a production deployment signal.
- **TOML config, multi-provider LLM support.** Config references GPT-4o, Claude 3.5, and Qwen VL Plus. Provider support is configuration-driven rather than SDK-abstracted (unlike opencode's Vercel AI SDK approach). Depth of non-OpenAI provider support is a claim to inspect.

## Why clawfit should care

OpenManus sits at a structural junction the current registry does not cover well: a general-purpose Python agent framework that is neither a harness-over-existing-agent (L2) nor a pure capability plugin (L4), but a self-contained runtime with a modular agent specialization model, browser automation, code execution isolation, and MCP tool consumption — all accessible without a license gate. Several concrete scoring implications:

1. **Level 1 with multi-capability bundling blurs the L1/L2 boundary.** OpenManus installs as a Python package and runs as a single-agent or multi-agent session; it is not wrapping Claude Code or another runtime — it is the runtime. That makes it L1-primary. But the multi-agent `run_flow.py` and the inherited tool registry pattern push it toward L2 in a way similar to OpenHands (which this taxonomy should audit against). The shallow release history (3 vs. OpenHands' continuous release cadence) currently supports treating the L2 multi-agent mode as design intent, not a production-tested orchestration layer.

2. **MCP client posture is a distinct topology.** OpenManus consumes MCP servers for tools. This is architecturally different from a framework that hosts MCP servers (Ruflo, which acts as both client and server). For clawfit profiles specifying MCP tool integration, the distinction matters: OpenManus requires external MCP servers to be running — it does not bundle them. A `mcp_role: client` axis would surface this difference cleanly.

3. **Two-model config (text + vision) is not modeled in agents.json.** OpenManus's config explicitly separates text-LLM and vision-LLM endpoints. Current registry schema assumes one LLM per agent. Profiles involving vision tasks alongside code or browser work will encounter this gap if OpenManus is added without schema extension.

4. **No benchmark data makes scoring confidence low for performance-sensitive profiles.** The `task: qa` or `task: research` profiles in clawfit rely partly on demonstrated task performance. OpenManus cannot currently support evidence-based scoring on any benchmark axis — any entry in the registry would require a "performance: unverified" flag.

5. **The MetaGPT lineage and OpenManus-RL signal positions this as an upstream research feed.** MetaGPT X (MGX) is the production product from the same team; OpenManus may be the research testbed from which capabilities flow into MGX over time. Tracking OpenManus means tracking the MetaGPT team's research direction, which has been consistently ahead of general framework adoption patterns.

## Preliminary interpretation

Current best reading:

- **Level 1 — Base runtimes / primary agent surfaces** (primary). OpenManus is a standalone Python agent runtime. It manages the agent run loop, tool execution, memory state, and LLM interaction directly — it is not a harness over another runtime. Specialized agents (`BrowserAgent`, `DataAnalysis`, `SandboxManus`) are L1 sub-types, not independent products. The base runtime classification holds even though the feature surface extends into browser automation (L6-adjacent), code sandboxing (L7-adjacent), and MCP tool consumption (L4c-adjacent).
- **Level 2 — Meta wrappers / harnesses / orchestration layers** (weak secondary). The `run_flow.py` multi-agent pathway introduces sequential agent handoff — Manus delegates to DataAnalysis, which returns results. This is a rudimentary orchestration pattern. However, the pathway is explicitly flagged as unstable in the README, the release count is 3, and no parallel coordination or agent communication protocol is documented. Do not assign L2 primary or strong secondary at this time. Re-evaluate if `run_flow.py` stabilizes and adds parallel coordination.
- **Level 4 — Capability / skill / plugin / tool-use layer** (weak secondary, MCP consumer). The MCP client tooling and the `ToolCollection` registry pattern create a capability surface, but OpenManus is consuming capabilities rather than providing them. This is a different relationship to L4 than a pure tool plugin — it is closer to "runtime that ingests L4 components."
- Notable positioning: OpenManus is the closest general-purpose Python-native L1 alternative to OpenHands in the current taxonomy. OpenHands (~72k stars, Docker-sandboxed, continuous releases) is the production benchmark; OpenManus (~56k stars, 3 releases, Daytona sandbox) is the lighter-footprint alternative from a research team with a strong track record. The gap in release cadence and benchmark data is material for production profiles.

## Status

- High star count (56.2k) puts this above the observation threshold but below confident registry promotion. Primary blockers: (1) no benchmark data — performance on any standard task evaluation is unverified; (2) multi-agent mode explicitly flagged as unstable; (3) Daytona sandbox dependency status (hard vs. optional) unconfirmed; (4) multi-provider LLM support depth outside OpenAI not independently tested. Track at next scan cycle. Do not add to reference-levels.md — signal is strong but production depth is not yet independently verified. Reassess at v0.5+ or first benchmark publication.
