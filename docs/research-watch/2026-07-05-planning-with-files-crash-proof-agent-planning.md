# Research Watch: planning-with-files — File-Based Persistent Planning for AI Coding Agents

- Repo: https://github.com/OthmanAdi/planning-with-files (⭐24,623)
- Source: GitHub Trending Python daily, July 5 2026

## Why this is worth watching

At 24,623 stars with 16,000+ claimed developer installs, planning-with-files is the highest-starred pure planning/memory artifact tracked in this scan series — ahead of tracked L5 tools and behind only behavioral skill aggregators. The core insight is architectural rather than novel: markdown files on disk survive context window boundaries, `/clear` commands, and process restarts in ways that in-memory or in-session state cannot. What distinguishes this from earlier planning-notepad approaches is the deterministic completion gate — the system claims to know when a plan is done, not just what remains to do. The combination of the SKILL.md cross-agent distribution standard with /plan-goal and /plan-loop composing against Claude Code's first-party slash command verbs (v2.1.139 `/goal`, v2.1.72+ `/loop`) is an integration surface worth tracking independently of the star count.

## What stands out immediately

- **Three-file schema with distinct roles, not a monolith:** `task_plan.md` holds the roadmap, phases, decisions, and current progress position; `findings.md` accumulates research and discovered facts; `progress.md` logs session outputs and test results. Each file has a defined write-authority and read-authority — this is a typed memory partitioning scheme, not a single scratch pad. Whether the schema is enforced programmatically or only by convention is not confirmed from available sources.
- **Deterministic completion gate as the primary architectural claim:** The system is described as having a `check-complete` evaluation that produces a definitive termination signal — not merely a progress indicator or confidence score. This would be a meaningful distinction from tools that end plans when context runs out or when the agent decides it is done. The implementation of `check-complete` (rule-based, LLM-judged, test-gated, or hybrid) is not specified in available sources and constitutes the claim most requiring independent verification.
- **/plan-goal composes with Claude Code's /goal (v2.1.139):** The slash command derives a termination condition from the active `task_plan.md` rather than requiring the user to specify one manually at session start. This implies the tool reads Claude Code's internal `/goal` contract and populates it from file state — a non-trivial integration that depends on Claude Code's slash command API surface remaining stable.
- **/plan-loop composes with /loop (v2.1.72+) on a 10-minute default tick:** Each tick re-reads the three planning files and runs `check-complete`. This is a polling-based autonomous continuation loop, not an event-driven one. The 10-minute interval is a default; whether it is configurable and whether the tick reads filesystem changes atomically (relevant when a human edits a file mid-tick) is not confirmed.
- **SKILL.md cross-agent distribution standard:** The tool claims compatibility with 60+ agents via the SKILL.md installation convention. SKILL.md is an emerging standard also observed in `virgiliojr94/book-to-skill` (tracked 2026-07-01) — this is the second tracked tool explicitly citing SKILL.md as its multi-agent distribution mechanism. Two independent signals for SKILL.md as a cross-agent skill standard is the threshold worth noting; it does not yet meet the two-signal rule for a named sub-type but is one additional signal away.
- **"Manus-style persistent planning" is a named design reference, not an origin claim:** The description uses "Manus-style" to position the approach within a recognizable pattern from Manus AI's task-execution model, where planning state is externalized to files the agent can read and write across sessions. The claim is about design lineage and expected behavior, not that this is a Manus fork or integration.
- **Multi-agent shared state on disk:** Multiple agents (or multiple sessions of the same agent) can read the same three files simultaneously. There is no mention of locking, conflict resolution, or merge semantics for concurrent writes. For single-agent sequential use this is not an issue; for the multi-agent shared-state claim, absence of a concurrency model is a gap.
- **16K+ developer install claim is not independently verifiable:** The number is not derivable from GitHub stars, fork count, or any public registry download counter cited in available sources. It may be a PyPI/npm install count, a survey, or a self-reported figure from the author. Treat as promotional until sourced.

## Why clawfit should care

**Level 5 memory layer has an underspecified planning sub-type.** The current L5 taxonomy covers MCP context tools and search/retrieval systems but has no slot for "structured planning artifacts" as a memory form. planning-with-files is the second tool after `framein` (tracked 2026-06-30) to treat planning-state persistence as the primary product — not a side effect of an LLM session, but an explicit file-based contract. These two tools together constitute a two-signal cluster for "file-based planning persistence" as a named L5 sub-type.

**The SKILL.md distribution axis is forming.** `book-to-skill` (tracked 2026-07-01, 7.4k★) and planning-with-files (24.6k★) both use SKILL.md as their cross-agent installation contract. If a third tool cites SKILL.md as its distribution mechanism, this becomes a durable L4b/L5 crossover pattern worth annotating in the canonical taxonomy: SKILL.md is how a planning or memory artifact is *delivered*, while its runtime behavior sits in L5.

**The /plan-loop tick pattern is a new autonomy axis for L5 tools.** Current L5 tools in the registry (codebase-memory-mcp and similar) are passive — they respond to queries but do not self-invoke. A 10-minute polling loop with a `check-complete` gate is a lightweight autonomous execution pattern. The clawfit `statefulness` axis currently captures `session` vs. `stateless` but has no slot for "self-invoking on a schedule." If this pattern recurs, `autonomy_mode: reactive | scheduled | event_driven` is a candidate axis.

**Registry field implications:** A registry entry for planning-with-files would require: `tasks: [code-gen, research]`; `statefulness: persistent` (files survive sessions); `network: offline` (pure filesystem, no API calls implied); `setup_complexity: low` (SKILL.md install); no `latency` axis applicable (planning state, not inference). The `check-complete` mechanism would need a `completion_gate` field that does not currently exist.

## Preliminary interpretation

Current best reading:

- **Level 5 primary — Memory / context layer:** The three-file schema is a typed, crash-proof, multi-session planning memory. This is the same level as codebase-memory-mcp and framein, but with a distinct sub-type: structured planning artifacts with defined read/write roles per file, rather than vector retrieval or session handoff contracts. The deterministic completion gate is the architectural differentiator if the implementation is non-trivial.
- **Level 4b secondary — Capability / skill layer:** SKILL.md installation makes planning-with-files a cross-agent installable skill rather than a standalone tool. The slash commands (/plan-goal, /plan-loop) are the delivery surface. This is the same layer classification as book-to-skill; both use SKILL.md as the distribution mechanism. L4b captures the installability; L5 captures what the skill actually does at runtime.
- **Level 3 tertiary weak — Team harness / governance:** The deterministic completion gate is a governance function — it defines when a task is done in a way the agent cannot override by drifting. If `check-complete` is implemented as a deterministic rule or test gate rather than an LLM judgment call, this would be a genuine L3 governance artifact at minimum scope. Currently unverified; noted as a weak secondary signal.

Comparison notes: `framein` (tracked 2026-06-30, L2 primary) is the closest structural analogue — both persist agent work-state to local files across session boundaries. The distinction is scope: framein targets multi-agent *handoff* contracts with a Challenge/Validate evaluation phase; planning-with-files targets single-agent or loosely-coordinated multi-agent *planning continuity* across restarts and context clears. They are complementary, not redundant. `virgiliojr94/book-to-skill` (tracked 2026-07-01) shares the SKILL.md distribution mechanism but operates in a different sub-layer (knowledge ingestion vs. planning state).

## Claims to verify

- **Deterministic completion gate implementation:** `check-complete` is described as producing a definitive termination signal, but whether this is rule-based (e.g., all tasks in task_plan.md marked complete), test-gated (e.g., all test suites pass), LLM-judged, or a combination is not specified in available sources. The distinction matters: an LLM-judged gate is probabilistic; a test-gated check is deterministic. The architectural claim rests on which implementation is actually used.
- **60+ agent compatibility via SKILL.md:** The claim implies SKILL.md is a stable, documented standard with broad adoption. Available sources confirm SKILL.md exists and is used by at least two tools (planning-with-files, book-to-skill), but whether 60+ named agents have tested or documented compatibility — as opposed to the SKILL.md install pattern working incidentally — is not confirmed.
- **/plan-goal and /plan-loop integration depth with Claude Code:** These slash commands claim to compose with Claude Code's `/goal` (v2.1.139) and `/loop` (v2.1.72+). Whether this is deep API integration (reading Claude Code's internal goal-tracking state) or surface-level prompt injection (generating a `/goal` invocation from file content) significantly changes the fragility of the integration under Claude Code version changes.
- **Multi-agent shared state concurrency:** The claim that multiple agents can share the three files simultaneously does not address concurrent write scenarios. Whether this works reliably in practice for multi-agent use cases — vs. a single agent reading its own prior context — is not confirmed.
- **16K+ developer install count:** Source and methodology for this figure not identified. Not independently verifiable from available public data.
- **10-minute tick atomicity:** When /plan-loop re-reads planning files on a tick, whether it reads a consistent snapshot (relevant if files are being written by an agent mid-task) is not specified.
