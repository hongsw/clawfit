# Research Watch: whichllm — Hardware-Aware Local LLM Picker with Recency-Weighted Benchmark Ranking

- Repo: https://github.com/Andyyyy64/whichllm (1.7k stars, MIT, Python 100%, v0.5.7 on 2026-05-19)
- Also see: GeekNews #17 (2026-05-24, 65 points — discovery source); `docs/research-watch/2026-03-28-llmfit-fit-navigator.md` (sibling fit-navigator concept); `docs/research-watch/2026-05-05-manifest-mnfst-smart-model-routing.md` (smart model routing comparable on the routing axis); `clawfit/scoring.py` (this project's own recommendation engine, structurally comparable)

## Why this is worth watching

whichllm is the closest structural analog to clawfit found in the watch queue to date: a CLI that takes a user environment as input and returns a ranked set of (model, runtime, hardware-fit) recommendations as output. Unlike clawfit, the input is auto-detected from local hardware probes rather than supplied as CLI flags, and the recommendation surface is restricted to local LLMs from HuggingFace rather than the (agent, LLM, hardware) triple. The recency-weighted benchmark merging methodology — five named leaderboards combined with explicit demotion of stale scores along each model's lineage — is a scoring pattern clawfit does not currently implement and which directly addresses a class of staleness errors clawfit's static registry is susceptible to.

## What stands out immediately

- **Scope is local-LLM-only and runs entirely on the user's machine.** The tool's universe is HuggingFace-hosted local models — there is no path to cloud-API models (Claude, GPT-4o, Gemini). The hardware detection (`nvidia-ml-py` for NVIDIA, ROCm/dbgpu for AMD, Metal for Apple Silicon, CPU AVX/cores, RAM, disk) is genuine local-hardware probing, not user-declared specs. This is a narrower scope than clawfit's (which also covers cloud cost-per-1k pricing) but deeper within that scope: clawfit treats hardware as a coarse `cloud | edge | on-prem` category with a single latency tier, while whichllm reads actual VRAM, AVX-512 presence, and disk space to decide model fit.

- **Hardware simulation mode (`--gpu "RTX 4090"`) supports purchase-planning queries.** This is a non-trivial UX affordance: a user evaluating a hardware upgrade can query "what could I run on X" before buying. clawfit's static `hardware.json` registry can do this through manual entry edits, but does not expose a "hypothetical hardware" query as a first-class CLI mode.

- **Five-source benchmark merge with explicit tier separation.** Current tier (LiveBench, Artificial Analysis Index, Aider) is refreshed live; frozen tier (Open LLM Leaderboard v2, Chatbot Arena ELO) is treated as stable historical signal; a separate multimodal/vision index is used for image-capable models. The two-tier "current vs frozen" split is an explicit acknowledgement that benchmark recency matters differently per source — Open LLM Leaderboard v2 is no longer updated and is treated as a stable historical baseline, while LiveBench/Aider/Artificial Analysis are treated as live signals.

- **Recency demotion along model lineage is the most distinctive scoring element.** The documented rule: "Stale leaderboards are demoted along each model's lineage, so a 2024 model can't outrank a current-generation one on an outdated score." Operationally this means a 2024 model with a high Chatbot Arena ELO from 2024 cannot beat a current-generation model whose score on a more recent benchmark is weaker in absolute terms but more recent. This is structurally a recency penalty applied to evidence freshness rather than to the model itself. Claim to inspect: how the lineage relationship is determined (HuggingFace family metadata, model card parsing, or hardcoded family trees) is not documented in the README extract — the correctness of the recency demotion depends entirely on correctly identifying which model is the "successor" to which.

- **Scoring formula has six explicit components.** From the documentation: benchmark quality (merged from five sources), model size (log₂-scaled), quantization penalties, evidence confidence multiplier (×0.55–1.0 depending on direct/inherited/self-reported), runtime fit (full GPU 1.0, partial offload ×0.72, CPU-only ×0.50), speed relative to a usability floor (±8 points), with source trust and popularity as tie-breaker. The runtime-fit multipliers (0.72 partial offload, 0.50 CPU-only) are calibrated penalties for degraded execution paths — a level of granularity that clawfit's `_latency_score` and `_cost_score` do not currently express.

- **Evidence confidence multiplier is a named axis.** Scores carry a ×0.55–1.0 multiplier based on whether the benchmark evidence is direct (the model itself was benchmarked), inherited (a related model in the same family was benchmarked and the score is propagated), or self-reported (vendor-claimed without independent verification). This is the first tool in the watch queue that surfaces benchmark provenance as an explicit numerical scoring factor. clawfit does not currently track evidence provenance per registry entry — the `reference-notes/evidence-schema.md` exists as a forward-looking schema but is not wired into scoring.

- **Quantization-aware: GGUF (llama-cpp-python), AWQ/GPTQ (transformers), FP16/BF16.** The tool knows that a model has multiple quantization releases and that quantization affects both fit (smaller VRAM footprint) and quality (penalty). This is an axis entirely absent from clawfit's current `llms.json` schema, which lists a model as a single entry with a single `cost_per_1k_tokens` value and no quantization breakdown.

- **Caching with explicit TTLs: 6h for models, 24h for benchmarks.** Disk caching is documented, not implicit. The model cache is shorter than the benchmark cache, reflecting that HuggingFace model availability changes faster than benchmark scores. This is a reasonable engineering choice and a useful reference for how clawfit might handle live data when it eventually graduates from a fully static JSON registry.

- **Execution surface is intentionally minimal but present.** `whichllm run` downloads and starts an interactive chat session for the selected model; `whichllm snippet` emits ready-to-run Python inference code. The tool is primarily a recommender, but the inclusion of `run` blurs the L7 (recommendation) and L1 (execution surface) boundary. Claim to inspect: whether `whichllm run` is a thin wrapper over llama-cpp-python / transformers or whether it implements its own loader.

- **1.7k stars, MIT, Python 100%, v0.5.7.** Below the 5k registry threshold; above the 100-star watch threshold. Discovery source is GeekNews (Korean tech aggregator) at 65 points — moderate but not breakout traction. The version number (0.5.7) signals pre-1.0 API and the absence of stability guarantees.

## Why clawfit should care

**1. Direct structural overlap with clawfit's recommendation mission — narrow but deeper.** clawfit's recommendation pipeline is `load → filter → score → rank → output` over (agent, LLM, hardware) triples. whichllm's pipeline is structurally identical but over (model, runtime, hardware-fit) triples, with the agent dimension absent and the LLM universe restricted to HuggingFace local models. The two tools occupy distinct but adjacent slots: clawfit is broader (includes agents and cloud LLMs), whichllm is deeper within local-model selection. This is the first tool in the watch queue that performs the same algorithmic shape as clawfit on a partially overlapping problem domain — making methodology borrowing especially clean.

**2. Recency demotion is a scoring pattern clawfit currently lacks and would benefit from.** clawfit's registry is static JSON with no notion of when a model entry was added, when its benchmark scores were captured, or whether a successor model exists. Adding an explicit recency-weighted scoring component — even a coarse "year of LLM release" demotion factor — would address a real staleness risk: a registry entry for GPT-4 captured in 2024 should not beat a 2026 entry purely because the older entry has settled into a higher historical position. The whichllm lineage demotion is a more sophisticated version of this; the simpler "release year decay" version would be a reasonable starting point for clawfit.

**3. Evidence confidence multiplier (×0.55–1.0) is a scoring axis worth adopting.** clawfit's `reference-notes/evidence-schema.md` defines structured evidence fields but the scoring function does not currently consume them. whichllm's three-tier evidence weighting (direct / inherited / self-reported) is a minimal viable implementation of evidence-aware scoring. The same three tiers map cleanly onto clawfit's evidence sources: direct = independent benchmark cited; inherited = same-family model evidence; self-reported = vendor blog claim. Implementation would be a per-source multiplier in `_cost_score` or a new `_evidence_score` component.

**4. Quantization granularity is a registry gap clawfit has not addressed.** A local LLM is not a single entry but a family of (base model, quantization, runtime) tuples. clawfit's `llms.json` treats Llama 3 70B as one entry; in practice the choice between Q4_K_M GGUF on llama.cpp vs. AWQ on transformers vs. FP16 on vLLM is a substantial scoring question. whichllm's quantization-aware scoring is a model for how clawfit's registry schema could evolve when local-model coverage becomes a priority. Today clawfit's `network: offline` profile would benefit most from this — that branch of the recommendation tree currently underspecifies what is actually running.

**5. Auto-detection vs. user-declared input is a UX axis clawfit could expose.** clawfit requires the user to declare `--hardware`, `--network`, `--latency`, `--budget`. whichllm reads `nvidia-ml-py` and infers most of these. A `clawfit recommend --detect` flag that probes the local environment for available hardware tier would lower the friction for first-time users and reduce mis-specification errors. The cost is a platform-specific dependency surface (nvidia-ml-py on Linux, Metal probe on macOS) — non-trivial but well-bounded.

**6. Scope-overlap implication: clawfit and whichllm could compose rather than compete.** A user pipeline could plausibly be: clawfit recommends the agent + LLM family + hardware tier → whichllm refines the specific local-model + quantization choice when the LLM selection lands on a local runtime. The two tools occupy non-overlapping decision points within the same workflow. This is worth recording as a composition pattern: clawfit operates at the layer of "what kind of LLM and where," whichllm operates at the layer of "which specific HuggingFace model and which quantization." No integration exists today; the composition is conceptual.

## Preliminary interpretation

Current best reading:

- **Level 7 — Infrastructure / hardware / edge layer (primary).** whichllm's first-order function is hardware-aware model selection for local execution: it probes real hardware (NVIDIA/AMD/Apple Silicon GPUs, CPU AVX support, RAM, disk) and produces hardware-fit-aware recommendations. The scoring formula's runtime-fit multipliers (full GPU 1.0, partial offload 0.72, CPU-only 0.50) operate directly on hardware execution paths. This is L7's definitional territory: tooling whose recommendations are gated by physical hardware capability. The presence of `whichllm run` (interactive chat) introduces a weak L1 secondary read but is not the primary function.

- **Cross-cutting recommendation-engine axis (companion read).** The stronger architectural reading is that whichllm sits in the same conceptual slot as clawfit itself: a recommendation engine that ranks options against user constraints. clawfit is not currently placed on the 7-layer map (it is the map's author, not a member), and the same applies to whichllm in its purest function. The L7 classification captures whichllm's hardware-fit specialty; the cross-cutting recommendation-engine read captures its algorithmic role. Both are valid lenses.

- **Not L1:** `whichllm run` is a convenience execution surface, not the tool's primary function. The vast majority of the tool's surface area is recommendation, not agent execution.

- **Not L5:** No memory, MCP, or context management is involved. The tool operates pre-execution on static benchmark and hardware data.

- **Not L6:** No retrieval or knowledge layer involvement.

- Notable subcategory candidate: **hardware-aware local-model recommender** is a narrow L7 sub-type. Two other tools occupy adjacent L7 territory: AMD GAIA (`docs/research-watch/2026-04-14-amd-gaia-local-agent-hardware-stack.md`) and LiteRT-LM (`docs/research-watch/2026-04-06-litert-lm-on-device-llm-runtime.md`) — both are execution-substrate tools (they run models), while whichllm is a selection-substrate tool (it picks which model to run). The sub-type "selection vs. execution" is a finer distinction within L7 that may be worth naming if a second hardware-aware recommender appears.
